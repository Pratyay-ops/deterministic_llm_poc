# Deterministic LLM inference on a GB10 - findings (2026-10-08)

## Summary

At temperature 0 - the setting usually assumed to be deterministic - a standard vLLM server gave **many
different answers to the same question** once other requests shared the server: up to 172 different
answers out of 200 identical requests. Turning on vLLM's batch-invariant mode (`VLLM_BATCH_INVARIANT=1`)
made every answer **bit-for-bit identical** for all prompts and both models tested, **at no measurable
speed cost** on the GB10. The cause and the fix match Thinking Machines Lab's analysis (*Defeating
Nondeterminism in LLM Inference*, 2025): results depend on how many requests are batched together, and
batch-invariant kernels remove that dependence.

## Setup

- Hardware: one Dell Pro Max GB10 (NVIDIA GB10, Blackwell, 128 GB unified memory). Software: vLLM 0.31.0
  (`vllm/vllm-openai:v0.31.0`), DGX OS 7.2.3.
- Prompts: our 8 prompts (`configs/prompts/my_prompts.txt`): system design, Python code, algorithms,
  incident analysis, database comparison, a haiku, a biography, SQL lineage extraction to JSON.
- Method: every prompt sent N times **at the same time to one server, mixed with the other prompts** (as a
  shared server sees it), temperature 0, up to 1000 tokens; first with the default vLLM kernels, then with
  batch-invariant mode. Answers compared token by token and on the exact float values of their logprobs.

## Results

**Qwen3-8B** (8 prompts x 200 requests per mode, 1600 requests per mode, 0 failed):

| prompt | default vLLM: different answers | first difference at token | batch-invariant: different answers |
|---|---|---|---|
| distributed rate limiter | 172 / 200 | 29 | **1 / 200** |
| thread-safe LRU cache (code) | 97 / 200 | 62 | **1 / 200** |
| longest increasing subsequence | 116 / 200 | 50 | **1 / 200** |
| microservices failure analysis | 154 / 200 | 41 | **1 / 200** |
| database paradigms | 126 / 200 | 95 | **1 / 200** |
| haiku | 1 / 200 | - | **1 / 200** |
| Richard Feynman | 143 / 200 | 59 | **1 / 200** |
| SQL source/target tables (JSON) | 5 / 200* | 45 | **1 / 200** |

\* the 165 copies of the most common SQL answer still had 141 different sets of logprobs underneath.

**Qwen3-30B-A3B-Instruct-2507** (mixture of experts; 8 prompts x 100 requests per mode, 0 failed):
default vLLM 7-89 different answers per 100 (**8 of 8 prompts** nondeterministic, first differences as
early as token 11); batch-invariant **1 of 100 for every prompt**.

**Speed (same work in both modes):** Qwen3-8B 896 -> 1019 output tokens/s; Qwen3-30B-A3B 467 -> 464
tokens/s. Determinism was free here, unlike the 1.6-2.1x slowdown reported for data-center GPUs - vLLM
0.31 ships kernels tuned for this GPU class.

## What the differences look like

Not just wording - the same question at temperature 0 produced:
- different code: `from typing import ..., Tuple, Union` vs `..., Tuple, List, Union` (LRU cache);
- a different root cause: "Inefficient Load Balancing and Resource Starvation" vs "Load-Dependent
  Throttling and Resource Contention" (incident analysis);
- different JSON content: "filtering by cycl_time_id" vs "filtered by cycl_time_id" (SQL lineage);
- different document structure: "High-Level Architecture" vs "Distributed Architecture" (rate limiter).

## Why it happens (supporting measurements)

- **Batch size changes the answer:** the rate-limiter prompt alone vs. hidden among 2-128 other requests -
  default vLLM changed the answer at batch sizes 8, 16 and 32 (diverging at token 140 or 209);
  batch-invariant mode was identical at every batch size tested (1-64).
- **Kernels are repeatable but not batch-invariant:** a single matrix multiplication gave the same bits in
  1000 repeats, yet a row's result changed with the number of rows in the batch; PyTorch's "deterministic"
  flags do not fix this, batch-invariant kernels do.
- **Root cause in one line:** floating-point addition is not associative - summing the same 8 numbers in
  different orders gives 102 different results.
- **Realistic load exposes more:** 200 identical requests on their own produced 7-12 different answers;
  the same prompts mixed with others produced up to 172 - testing with identical requests underestimates
  the problem.

## Limits and caveats

- Determinism holds for the same weights, vLLM build, GPU type and server settings; another GPU or vLLM
  version can give different (again deterministic) answers. Re-validate after upgrades.
- vLLM 0.31's batch-invariant mode does not support hybrid linear-attention / Mamba models (Qwen3.5, 3.6,
  3.8, Nemotron-H); dense and mixture-of-experts transformers (Qwen3-8B, Qwen3-30B-A3B) work.
- Prefix caching was not validated with batch-invariant mode and is kept off.
- The repository's own alternative ("custom" fixed-size chunks through cuBLAS) is not sufficient on this
  GPU: a row's result can still depend on its position inside a chunk. vLLM's batch-invariant mode and
  Thinking Machines' library are.
- One machine, one run per mode; speed numbers come from the mixed-load runs, not a dedicated benchmark.

## Recommendation

For uses that need repeatable answers - testing and evaluation of LLM features, audits, regulated or
customer-facing outputs, debugging - serve with vLLM's batch-invariant mode at temperature 0 (or a fixed
seed) on the validated configuration. On the GB10 with Qwen3-8B or Qwen3-30B-A3B it costs no throughput.
